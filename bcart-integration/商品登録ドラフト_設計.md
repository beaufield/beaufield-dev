## §1 決定済みの運用方針（2026-07-09 Takashi確認済み・変更時は要再確認）

1. **対象範囲**: 未登録約1,280件を**仕入先ごとにバッチ処理**。優先順位は最終売上日が近い順（第1波: 1年以内 → 第2波: 2年以内）。「Bモールに載せない商品」は既存の対応不要マークで除外する運用（今後も同様）
2. **画像**: メーカーサイトの商品ページURL・画像候補URLを「参考資料」としてドラフトに添付するのみ。**自動ダウンロード・転載はしない**（Takashiが手動で加工してアップする前提）。画像実体のアップロードAPIは存在しない（§7-13参照）
3. **レビュー**: シリーズのまとめ方＋説明文を**1画面で一括レビュー**（そのためドラフト生成時に説明文まで作り込む）
4. **非表示登録**: 承認後の登録は必ず非表示状態。Takashiの最終確認（＋画像アップ）後に表示化
5. **承認の担保**: AIが使えるAPIキー（機能E方式）では読み取り＋ドラフト保存まで。**登録・公開・却下の実行はポータルセッション認証必須**（＝人間のみ）

## §2 全体フロー

```
① 候補抽出    GAS: getDraftCandidates（未登録・除外済み・仕入先＆最終売上日フィルタ）
② 実例取得    GAS: getRegisteredExamples（既存products+setsの紐づき実績＝few-shot教師データ）
③ シリーズ推定 Claude（bcart-draftスキル）: A/B/C分類＋確信度＋根拠
④ ドラフト生成 Claude: 商品名・カテゴリ・説明文・参考URL（Web検索込み）
⑤ 保存・通知   GAS: saveDrafts → シート保存 → LINE WORKS通知（Webhook設定時のみ）
⑥ レビュー     master-tool「登録ドラフト」タブ: 承認/修正/却下  ←フェーズ2
⑦ 登録実行     承認分のみ既存関数で非表示登録＋説明文PATCH      ←フェーズ2
⑧ 公開        Takashiが画像を管理画面でアップ → タブから表示化 ←フェーズ2
```

## §3 前提知識（データモデル）

- **Bカートの商品構造**: `products`（親商品）1 : N `product_sets`（バリエーション＝セット）。社内商品コードは**セット側の `product_no`** と対応する。「シリーズを1商品にまとめる」＝1つの products に複数の product_sets をぶら下げること
- **照合キーの正規化**: `String(parseInt(code, 10) || code)`（先頭ゼロ差を吸収。calcDiffs / normalizeProductNo と同じ）
- **商品.CSVの実際の列名**（calcDiffsで使用実績のあるもの）: `コード`（⚠️「商品コード」ではない）/ `商品名` / `略称` / `かな` / `単位名` / `仕入先CD` / `仕入先名` / `売上単価` / `仕入単価` / `定価１`（⚠️全角の１。フォールバックで `定価1` も見る）/ `廃番` / `JANCD` / `在庫有無` / `最終売上日` / 大分類系列
- **未登録の定義**（calcDiffsと同一基準）: CSVに存在し、product_no がBカートの product_sets に無いもの。除外: 廃番（`'1'`/`'TRUE'`/`'廃番'`）・売上単価0円・対応不要マーク済み（ignoreMap）・**在庫有無が「する」以外**（差異一覧画面のデフォルトフィルター`stockFilter='する'`と揃える。⚠️2026-07-09時点の本設計書にはこの除外ルールが漏れており、2026-07-12実装時にフェーズ1のGAS実装で発覚・追加した）

### シリーズ推定の3分類

| 分類 | draft_type | 登録時に使う既存関数 |
|------|-----------|-------------------|
| A. 既存商品にセット追加 | `add_to_existing` | `addSetToProduct`（既定でset_flag非表示） |
| B. 複数コードを1商品にまとめて新規登録 | `new_product`（セットN件） | `bulkRegisterProduct`（親flag非表示） |
| C. 単独で新規登録 | `new_product`（セット1件） | `bulkRegisterProduct`（セット1件で呼ぶ） |

## §4 フェーズ1: ドラフト生成基盤（GASアクション＋シート＋スキル）

### 4.1 新規シート（既存の履歴シートと同じスプレッドシート・`getOrCreateSheet` で自動生成）

**`登録ドラフト`**（1行=1商品案）:

| 列 | 内容 |
|----|------|
| draft_id | `D20260709-001` 形式（GAS側で採番） |
| status | `下書き` / `承認` / `却下` / `登録済` / `公開済` |
| draft_type | `new_product` / `add_to_existing` |
| target_product_id | add_to_existing時の既存商品ID（それ以外は空） |
| product_name | Bモール向け商品名（AI提案・レビューで編集可） |
| category_id | カテゴリID（AI提案） |
| feature_id1 / feature_id2 / feature_id3 | 特集ID（AI提案・空可） |
| description | 説明文（AI生成・100〜150字・プレーンテキスト） |
| confidence | `高` / `中` / `低` |
| reasoning | 判定根拠文 |
| ref_urls | メーカーページURL・画像候補URL（改行区切り） |
| supplier_cd / supplier_name | 仕入先 |
| created_at / reviewed_at / registered_product_id | 管理用 |

**`登録ドラフト_セット`**（1行=1商品コード）:

| 列 | 内容 |
|----|------|
| draft_id | 親ドラフトID |
| code | 社内商品コード（正規化済み） |
| set_name | セット名（AI提案。例「1000ml」「No.5 アッシュ」） |
| jan / unit_price / jodai / shiire / unit | 商品.CSVから転記（JANCD/売上単価/定価１/仕入単価/単位名） |
| last_sale_date | 最終売上日 |

### 4.3 アクションcontract

共通: リクエストはJSON POST。claudeActions系は `"apiKey"` を含める。レスポンスは `{ok: true, ...}` / `{ok: false, error: '...'}`。

#### getDraftSupplierSummary — バッチ計画用の仕入先別件数

```json
// req
{ "action": "getDraftSupplierSummary", "apiKey": "***" }
// res
{ "ok": true, "totalUnregistered": 1280,
  "suppliers": [
    { "supplierCd": "123", "supplierName": "（仕入先名）",
      "countWithin1y": 24, "countWithin2y": 41, "countTotal": 87 }
  ] }
```
実装: `loadCsvFromDrive` + `bcartGetAll('/product_sets')` + `getIgnoreMap` から未登録を抽出（§3の除外基準）→ 仕入先CDで集計。countWithin1y降順ソート。

#### getDraftCandidates — ドラフト対象の取得

```json
// req
{ "action": "getDraftCandidates", "apiKey": "***",
  "supplierCd": "123", "lastSaleWithinDays": 365, "limit": 50, "offset": 0 }
// res
{ "ok": true, "total": 24,
  "candidates": [
    { "code": "4567", "name": "商品名", "kana": "しょうひんめい", "ryakusho": "略称",
      "unit": "本", "supplierCd": "123", "supplierName": "（仕入先名）",
      "price": 1200, "kouri": 1800, "shiire": 900, "jan": "4901234567890",
      "lastSaleDate": "2026/05/12", "stockManagement": "する" }
  ] }
```
実装: 未登録抽出（同上）→ supplierCd・最終売上日でフィルタ → 最終売上日**降順**でlimit/offset。価格はカンマ除去済み数値で返す。⚠️`最終売上日`の日付形式は実装時に実データ先頭5行を `Logger.log` で確認してからパースを書くこと（§7-9）。

#### getRegisteredExamples — few-shot用の既存登録実例

```json
// req
{ "action": "getRegisteredExamples", "apiKey": "***", "supplierCd": "123", "maxProducts": 80 }
// res
{ "ok": true,
  "examples": [
    { "productId": 456, "productName": "〇〇トリートメント", "categoryId": 12,
      "featureIds": [3, null, null],
      "sets": [ { "setId": 789, "productNo": "4560", "setName": "250ml" },
                { "setId": 790, "productNo": "4561", "setName": "1000ml" } ] }
  ],
  "categories": [ { "id": 12, "name": "トリートメント" } ] }
```
実装: CSVから code→仕入先CD マップを作り、`bcartGetAll('/product_sets')` を product_id でグルーピング。**指定仕入先のコードを1つ以上含む商品**を返す（複数セット持ちを優先ソート）。該当0件なら全体から複数セット持ち商品を maxProducts 件サンプリングして返す（`fallback: true` を付ける）。categories は `getCategories` を内部呼び出しして同梱（Claudeがcategory_idを提案するため）。

#### saveDrafts — ドラフト保存

```json
// req
{ "action": "saveDrafts", "apiKey": "***",
  "drafts": [
    { "draftType": "new_product", "targetProductId": null,
      "productName": "〇〇カラー剤", "categoryId": 12,
      "featureId1": 3, "featureId2": null, "featureId3": null,
      "description": "（100〜150字）", "confidence": "高",
      "reasoning": "既存商品ID 456 と同シリーズのセット構成パターンに一致…",
      "refUrls": ["https://maker.example.com/product/xxx"],
      "supplierCd": "123", "supplierName": "（仕入先名）",
      "sets": [
        { "code": "4567", "setName": "No.5", "jan": "4901234567890",
          "unitPrice": 1200, "jodai": 1800, "shiire": 900, "unit": "本",
          "lastSaleDate": "2026/05/12" } ] }
  ] }
// res
{ "ok": true, "saved": 12, "skipped": [ { "code": "4568", "reason": "既存ドラフトD20260701-003に含まれるためスキップ" } ],
  "draftIds": ["D20260709-001"] }
```
実装:
- draft_id採番: `'D' + yyyyMMdd + '-' + 3桁連番`（当日既存の最大値+1）
- status=`下書き`・created_at=now で2シートへ書き込み
- **重複ガード**: セットの code が既存の `下書き`/`承認`/`登録済` ドラフトに既に含まれる場合、そのドラフト全体をskippedに回して保存しない（部分保存はしない）
- 保存後、`LINEWORKS_WEBHOOK` 設定時のみ通知（既存 `weeklyCheck` の通知実装パターンを流用）: 「登録ドラフト N件保存（仕入先: 〇〇）レビューをお願いします」

name: bcart-draft

**接続情報**（スキル本文に手順として書く。実値は書かない）:
- GAS WebApp URL: `handover-secrets.md` の「GAS WebApp URL一覧」bcart-integration 行
- apiKey: Windows環境変数 `BCART_CLAUDE_KEY`（Userスコープ）。値をチャット・ログに出さない
- 呼び出しは **Bash + curl 推奨**: JSONボディを一時ファイル（スクラッチパッド）に書き、`curl -sL -H "Content-Type: application/json" --data-binary @body.json "$GAS_URL"`。`-L` 必須（GASのPOSTは302リダイレクトを返すため）。PowerShellを使う場合はUTF-8 bytes化と単一要素配列のアンラップ対策が必要（機能Eメモリ参照）→ curlの方が安全

**処理手順**:
1. 引数（仕入先名/CD・期間）が無ければ `getDraftSupplierSummary` を叩き、1年以内件数の上位を表で提示してユーザーに選ばせる
2. `getDraftCandidates`（lastSaleWithinDays=365。対象が尽きた仕入先は730で再実行）＋ `getRegisteredExamples` を取得。1バッチ最大50件
3. **シリーズ推定**（Claude自身が実施）。判定ルール:
   - **まずA（add_to_existing）を探す**: 商品名から容量・数量・色番（No.x / #x）・サイズ・入数表記を除いた「基本名称」が、既存親商品の名称またはそのセット群の基本名称と一致 → その productId へのセット追加
   - 残りのうち、同一仕入先内で基本名称が同じ未登録品同士 → B（1商品にまとめて new_product）
   - どれにも該当しない → C（単独 new_product）
   - セット名は差分部分のみ（例「1000ml」「No.5 アッシュ」）。既存実例のセット名の書き方に倣う
   - 商品名・categoryId・featureIdは同仕入先・同系統の既存実例から流用。実例が無ければ最も近い実例＋categoriesリストから選び confidence を下げる
   - confidence基準: `高`=既存実例と明確に一致 / `中`=名称パターンからの推定 / `低`=判断材料不足（レビュー必須の旨をreasoningに書く）
4. **説明文生成**（各ドラフト）: Web検索でメーカー公式商品ページを特定し、100〜150字・見出しや箇条書きなし・自然な文章・**検索で確認できない成分/数値/効能は書かない**（既存GAS `generateDescription` のプロンプト方針を踏襲。文面は「美容室・エステサロン向けBtoB商材の説明文」）。同時にメーカーページURL・画像候補URLを refUrls に収集。公式ページが特定できない場合は説明文を商品名からの合理的推測のみで書き、reasoningにその旨を明記
5. **保存前プレビュー**: A/B/C内訳・確信度低の一覧・まとめ提案（B分類）の構成を表で提示し、ユーザーOK後に `saveDrafts`
6. 結果報告: 保存件数・skipped・その仕入先の残件数

## §5 フェーズ2: レビュータブ＋登録実行（master-tool）

### 5.1 GASアクション（すべてポータルセッション認証）

#### getDrafts
`{ action, session, status?: '下書き', supplierCd? }` → 親＋セットをjoinしたドラフト一覧を返す。既定は status=下書き。

#### updateDraft
`{ action, session, draftId, productName?, categoryId?, featureId1..3?, description?, sets?: [...] }` → 該当行を上書き（setsを渡した場合は該当draft_idのセット行を全置換）。addHistory記録。

#### approveDraft（承認＝登録実行）
`{ action, session, draftId }` → **シートの現在値を正として**登録を実行:
- `new_product`: `bulkRegisterProduct` 相当を内部呼び出し（productFlag=`'非表示'`・setFlag=`'非表示'`）→ 成功後 `PATCH /products/{id}` で `description` を反映（⚠️registerProduct系はdescription非対応のため追加PATCH必須。PATCHパターンは既存 `updateProductAction` / `applyProductFields` に倣う）
- `add_to_existing`: `addSetToProduct` を各セットで呼ぶ（既定でset_flag非表示なのでそのまま）
- 成功: status=`登録済`・registered_product_id 記録・reviewed_at=now。部分失敗: bulkRegisterProduct内蔵のロールバック挙動に任せ、結果をそのまま返す（statusは下書きのまま）
- レスポンスに productId / setIds / 失敗詳細を含める

#### rejectDraft（却下）
`{ action, session, draftId, reason }` → status=`却下` ＋ **セットの各codeを `markIgnore`**（理由: `'登録ドラフト却下: ' + reason`）。以後の候補抽出から自動的に消える。

#### publishDraft（公開）
`{ action, session, draftId }` →
- `new_product`: 親 `flag: '表示'` ＋ 全セット `set_flag: '表示'` にPATCH
- `add_to_existing`: 該当セットのみ `set_flag: '表示'`
- status=`公開済`・addHistory記録

### 5.2 画面仕様（index.html 新タブ「登録ドラフト」）

- 既存タブの実装パターン（タブ定義・GAS呼び出し・カードUI）に倣う。認証は既存のポータルセッション機構をそのまま使用
- フィルタ: 仕入先ドロップダウン＋status（既定: 下書きのみ）
- **カード形式（1カード=1商品案）**:
  - 上段: draft_typeバッジ・確信度バッジ（高=緑/中=黄/低=赤）・商品名（インライン編集可）
  - add_to_existing の場合は追加先の既存商品名を表示

## §7 落とし穴・実装注意（must-read）

1. **CSV列名は `コード`**（HANDOVER.mdの列構成表には「商品コード」とあるが、calcDiffs実装は `row['コード']`）。`定価１` は**全角の１**（`row['定価１'] || row['定価1']` のフォールバック必須）
2. 照合キー正規化: `String(parseInt(code, 10) || code)`。新コードは必ずこれを通す
3. CSV価格はカンマ付き文字列 → `parseFloat(String(v).replace(/,/g, ''))`
4. **claudeActions配列（doPost冒頭）への追加はAI用4アクションのみ**。approve/reject/update/publish/getDrafts を追加すると承認担保が壊れる（絶対禁止）
5. **承認時の表示設定（v2.17.1〜）**: new_product/add_to_existingいずれも**親商品`flag`=非表示・セット`set_flag`=表示**で登録する（Takashi確定・2026-07-12）。親が非表示の間はセットが表示でも商品ページ自体出ないため実害なく、公開（画像アップ後の🌐ボタン）時にセット側の再設定が不要になる。※v2.17.0まではセットも非表示で登録していたが変更済み
6. registerProduct系は `description` を扱わない → 登録成功後に products へ追加PATCH
7. レート制限300req/300秒。`bcartGetAll` はページング済み・`Utilities.sleep(500)` パターンを踏襲。approveDraftは1商品単位なので問題なし
8. GAS 6分制限: getRegisteredExamples は仕入先絞り込み必須（products+sets全件取得は数十秒かかる。1回のアクション内で全件取得は2回まで）
9. `最終売上日` の日付形式は**実データで確認してから**パース実装（実装時にLogger.logで先頭5行確認）。参考: sales-db（商品.CSVと同源のデータ）では `YYYYMMDD` 8桁文字列で、**売上実績なしは `00000000`**（2026-07-11確認）。CSV側も同形式の可能性が高いが、`00000000` を「最近売れた」と誤判定しないこと
10. GAS WebAppのPOSTは302リダイレクト → curl は `-L` 必須
11. PowerShellから叩く場合: ボディをUTF-8 bytes化（日本語化け対策）・PS5.1の `ConvertTo-Json` は単一要素配列をアンラップするためJSON手動構築（詳細: 自動メモリ `project_bcart_claude_direct_edit.md`）
12. `DELETE /products/{id}` は registerProduct のロールバックで使用実績があるが、公式リファレンスに削除エンドポイントは載っていない。**DELETE挙動に依存した新規設計はしない**（既存ロールバックの流用のみ可）
13. **画像**: ファイルアップロードAPIは全109エンドポイントに存在しない。ただし `products.image` へのパス/URL文字列のAPI設定自体は可能（機能E imageBasePath 実績: `https://files.bcart.jp/beaufieldec/uploads/items/...` 形式）。実体アップロードは管理画面のみ → 本件では refUrls の参考提示に留める（§1-2）
14. コード修正は**全文差し替え**で提供（Takashiの確定ルール）。`VERSION` 定数をbump（フェーズ1実装時は v2.15.0 想定）
15. GitHub Publicリポジトリ: 仕入先実名・価格・URL実値・キーをコード/設計書/コミットに含めない
16. 実装完了時は `master-tool/HANDOVER.md` と `CLAUDE.md`（プロジェクト一覧の状態）を必ず更新
17. **Google Sheetsの数値自動型変換に注意**: `appendRow`でコード等の数字文字列を書き込むと、Sheetsが数値型として保持する。`getDataRange().getValues()`で読み戻した値をBCART API（product_no/jan_codeは文字列型必須）へそのまま渡すと422エラーになる。**API呼び出し直前に必ず`String()`で明示的に文字列化すること**。可能ならシート列自体に`setNumberFormat('@')`でテキスト書式を設定しておくと保険になる（2026-07-12 承認機能の実装で発覚。approveDraftが全件422になるバグの根本原因だった）
18. **美容師限定表示（view_group_filter）**: このBカートは美容師向け業務用品の卸サイトのため、多くの商品は一般会員（エステ等）に非表示にする必要がある（Takashi要望・2026-07-12）。`view_group_filter`フィールドに`'非会員,通常会員,1'`（非会員・通常会員はキーワード、`1`は個人会員=サロンエンドユーザーの表示グループID）を設定すると、美容室(id2)・社員(id10)にのみ表示される。書式は既存の例外表示機能（`master-tool/gas/Code.gs`の`VF_FILTER_VALUE`定数）と同一パターンを踏襲した。承認画面のカードに🔒チェックボックスで都度ON/OFF可能（既定ON）
    - ⚠️ **`view_group_filter`は`products`（親商品）と`product_sets`（セット）の両方に同名で別個に存在する**。管理画面の商品編集で見える「商品非表示設定」は**products側**のフィールド。v2.17.2ではproduct_sets側にしか設定しておらず反映されない不具合があり、v2.17.3でproducts側（`registerProduct`/`bulkRegisterProduct`のproductBody）にも設定するよう修正した。**v2.17.4でTakashi確認の結果「product_sets側の表示グループ別設定は不要」との要望を受け、product_sets側の設定は完全に削除しproducts側のみに一本化した**（new_productのみ対象。add_to_existingは既存商品自体のview_group_filterを変更しない）
