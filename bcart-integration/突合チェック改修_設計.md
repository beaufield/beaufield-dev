## 1. 目的と背景（なぜ改修するか）

突合チェックの目的は **「サロンに特価で販売しているのに、Bカートに特価設定が無い商品」を洗い出すこと**。
特価設定が漏れていると、サロンは通常価格で商品を選択・注文できてしまい、そのまま出荷されてしまう。この漏れをなくすのが最優先ゴール。

現状の問題（Takashiフィードバック 2026-07-17）:
1. ヘルプリンクが常時表示で、どの画面のヘルプか分かりにくい
2. 結果の文言が分かりにくい（「管理外の特価」等）。**販売履歴の話だと誤解された** — 実際は「Bカート上の特価設定 vs アプリのマスター」の設定同士の照合であることがどこにも書かれていない
3. テスト用得意先（99997/99998/99999等）がノイズとして混ざり、結果の意味が取れない → 除外設定が必要
4. 結果を見ても「次に何をすればいいか」が分からない → 対処への導線（画面遷移・アクション）が必要

### 確定済み仕様判断（Takashi確認済み・再確認不要）
- ヘルプは**案B**: 全サブビューでリンク表示を維持し、表示中サブビューに対応するguide.htmlの節へ直接ジャンプ。ラベルは「❓ この画面の使い方」
- 除外設定を新設（シート管理・結果行からワンクリック追加可）
- カテゴリ名・表示順を目的優先に全面変更（§4の文言コピーをそのまま使う）
- 結果から対処へ移れる導線を付ける（§5）
- **Phase 2（今回やらない）**: Bカート側の特価削除機能・設定漏れのその場一括反映

## 4. 改修B: 結果画面の再設計（文言はこのままコピーして使う）

### 4-1. 実行前の説明ボックス（renderSpAudit冒頭・常設）

```
🔍 このチェックが照合しているもの
Bカートの各商品セットに登録されている「特価設定」と、このアプリの特価マスター（導入サロングループ＋個別特価）を突き合わせます。
※ 販売履歴（いつ・何を売ったか）とは無関係です。「設定」同士の照合です。
※ 除外設定に登録した得意先はチェック対象外です（現在 N 件）。
```
- N は `getAuditExclusions` の件数（audit画面表示時に取得）
- 所要時間の文言は「十数秒〜1分ほどかかります」に更新（bcartGetAll並列化済みのため。「1〜2分」は廃止）

### 4-3. 各テーブル（この順・タイトル/説明文はこのまま使う）

**① 🚨 特価の設定漏れ — マスターでは特価のはずが、Bカートに設定がありません**
> このままだと対象のサロンは通常価格で注文できてしまいます。「反映画面を開く」から該当画面へ移動し、「BCART反映」を実行してください（保存しただけで反映し忘れている明細もここに出ます）。

列: 品番 / 商品セット名 / 得意先コード / 会員名 / マスター価格 / 出所 / 操作
- 操作列: 出所がグループ → `▶ 反映画面を開く`（`switchToSettings(group_id)` 呼び出し）／個別 → `▶ 個別特価を開く`（§5-1のgotoSpSubview）
- **特殊行**（BCARTに商品セット自体が無い場合）: 商品セット名を `⚠️ この商品はBカートから削除されています` とし、説明を「マスター側の該当行を削除してください」、操作は出所画面への遷移ボタンのみ

**② ⚠️ 金額ちがい — マスターとBカートで特価の金額が一致しません**
> どちらが正しいか確認してください。マスターが正しい場合 →「反映画面を開く」から再反映（Bカートを上書き）。Bカートが正しい場合 → マスター側の金額を修正してください。

列: 品番 / 商品セット名 / 得意先コード / 会員名 / Bカート価格 / マスター価格 / 出所 / 操作（①と同じ遷移ボタン）

**③ ❓ マスター未登録の特価 — Bカートに特価が設定されていますが、このアプリのマスターに記録がありません**
> Bカート管理画面で直接設定された特価などがここに出ます。正しい特価なら「マスターへ取り込む」で個別特価として記録してください。テスト用の得意先は「除外」ボタンでチェック対象から外せます。（Bカート側から特価設定を削除する機能は今後追加予定。それまではBカート管理画面で削除してください）

列: ☑選択 / 品番 / 商品セット名 / 得意先コード / 会員名 / 会員ID / Bカート価格 / 操作
- テーブル上部: `✔ 選択をマスターへ取り込む（個別特価に追加）` ボタン（§5-2）
- 操作列: `🚫 除外` ボタン（§6-4）
- 得意先コードが空の行（会員にext_idが無い）はチェックボックス無効＋title属性「得意先コードが無いため取り込めません（除外は可能）」

**④ ⏸ Bカート未登録の得意先 — 対応は不要です（情報）**
> マスターに登録済みですが、まだBカート会員になっていない得意先です。会員登録されると、次回の反映時に自動で特価が適用されます。

列: 得意先コード / 出所 / 操作（`🚫 除外` のみ）

## 5. 改修C: 対処への導線（画面遷移・アクション）

### 5-1. サブビュー遷移ヘルパー（index.html）
```js
function gotoSpSubview(view) {
  const btn = document.getElementById('sp-btn-' + view); // sp-btn-groups/settings/individual/audit
  if (btn) switchSpSubview(view, btn);
}
```
- グループ出所の行 → `switchToSettings(group_id)`（既存関数・グループ選択済みで設定画面が開く）
- 個別出所の行 → `gotoSpSubview('individual')`

### 5-2. マスターへ取り込み（新GASアクション `adoptUnmanagedPrices`）

**目的**: 「マスター未登録の特価」のうち正しいものを、個別特価シートに**反映済み扱い**で記録する（Bカート側には既に設定があるため、PATCHは一切送らない。applied_atを入れて「未反映」アラートを出さないのがポイント）。

Request:
```json
{ "action": "adoptUnmanagedPrices",
  "items": [ { "customer_code": "9999", "member_id": "10999", "member_name": "サンプルサロン",
               "set_id": "123", "product_no": "XXX-1008", "set_name": "サンプル商品100ml",
               "unit_price": 3465 } ] }
```
Response: `{ ok: true, added: n, updated: n, skipped: [<customer_code空でスキップした行の説明>] }`

実装仕様:
- `saveIndividualPrices` の行書き込みを参考にするが、**product_setsの再取得はしない**（set_id/product_no/set_nameはリクエストに全部載っているため。高速）
- dedupキーは既存と同じ `customer_code|set_id`。既存行あり→ price/member_id/member_name/updated_at を上書き＋ **applied_at=now**。新規→ appendRowで `[newId, code, member_id, member_name, set_id, String(product_no), set_name, price, nowStr, nowStr, '突合チェックから取り込み']`
- customer_code空のitemはスキップして skipped に理由を返す
- addHistory: type `個別特価取り込み(突合)`、after `新規n件/更新n件`
- フロント: 成功後、取り込んだ行を `spAuditResult.unmanaged` から除去し `renderSpAuditResult()` 再描画＋toast「n件をマスターへ取り込みました（個別特価・反映済み扱い）」

### 5-3. auditSpecialPrices レスポンス拡張（後方互換で追加のみ）
- `missing` / `mismatch` の各行に追加: `set_id`（文字列）, `source_type`（`'group'` | `'individual'`）, `group_id`（source_typeがgroupのときのみ）
  - 生成箇所: expectedマップ構築時に `{price, source}` → `{price, source, sourceType, groupId}` へ拡張
- `unmanaged` の各行に追加: `set_id`
- `summary.excluded`（除外された照合エントリ数）を追加
- 既存キー（unmanaged/mismatch/missing/pending/summary.*）は名前・型を変えない

## 6. 改修D: 除外設定（新機能）

### 6-1. 新シート `特別価格_突合除外`
| 列 | 内容 |
|----|------|
| exclude_id | `X` + timestamp36 + rand4（個別特価のID生成と同形式） |
| customer_code | 得意先コード（ext_id）。無ければ空 |
| member_id | Bカート会員ID。無ければ空 |
| label | 会員名（自動解決。解決できなければ空） |
| reason | 理由（例「テスト用」）。任意 |
| created_at | 登録日時 |

- 定数 `SHEET_SP_AUDIT_EXCLUDE = '特別価格_突合除外'` を追加し、`getOrCreateSheet` にヘッダー初期化branchを追加（ヘッダー行bold・背景#f3f4f6・setFrozenRows(1)、customer_code列は `setNumberFormat('@')`）

### 6-2. 新GASアクション（doPost switchに追加・特別価格系と同じ認証ゾーン）
- `getAuditExclusions` → `{ ok, exclusions: [{exclude_id, customer_code, member_id, label, reason, created_at}] }`
- `addAuditExclusion { code_or_id, reason }` → codeまたは会員IDどちらでも受ける1入力方式。解決ロジック:
  1. `fetchCustomersCached()` の byExtId で raw一致 → ダメなら正規化一致（§7の normCode_）
  2. byId で会員ID一致
  3. どちらも解決できなくても登録は許可（customer_codeに入力値・member_id空・label空。「未登録得意先」の除外に必要）
  - dedup: 既存行と customer_code または member_id が一致したら追加せず `{ok:true, duplicated:true}`
  - Response: `{ ok, exclude_id, resolved: {customer_code, member_id, label} }`
- `deleteAuditExclusion { exclude_id }` → `{ ok }`
- いずれも addHistory 記録（type `突合除外追加` / `突合除外削除`）

### 6-3. auditSpecialPrices への組み込み
- 冒頭で除外シートを読み、2つのSetを作る:
  - `excludedMemberIds`: member_id列の値 ＋ customer_code列をbyExtIdで解決できた会員ID（すべてString）
  - `excludedCodes`: customer_code列の正規化形（normCode_）
- フィルタ位置:
  - actual側ループ: `excludedMemberIds.has(mid)` → skip・excludedCount++
  - expected側（missing判定・セット消滅判定の両方）: 同上
  - pending: `excludedCodes.has(normCode_(code))` → skip・excludedCount++
- `summary.excluded = excludedCount`

### 6-4. UI（audit画面内）
- 実行ボタンの下に折りたたみセクション「🚫 除外設定（チェック対象外の得意先）— N件 ▼」（デフォルト閉。クリックで開閉）
  - 開くと: 一覧テーブル（得意先コード/会員名/理由/登録日/削除ボタン）＋追加フォーム（`得意先コードまたは会員ID` input ＋ `理由(任意)` input ＋ 追加ボタン）
  - 追加・削除後は一覧を再取得して再描画。**突合結果の再実行はしない**（次回実行から反映される旨を一覧下に注記:「※ 追加・削除は次回のチェック実行から反映されます」）
- 結果行の `🚫 除外` ボタン: `addAuditExclusion({code_or_id: customer_code || member_id, reason: '結果画面から追加'})` → 成功したら該当行を spAuditResult の当該配列から除去して再描画＋toast。**確認ダイアログは出す**（`confirm('「◯◯」を突合チェックの対象外にしますか？')`）

## 7. 落とし穴（必読）

1. **ext_id表記ゆれ**: Bカート会員のext_idは非ゼロ埋め・社内台帳はゼロ埋めの場合がある。コード照合は必ず正規化関数を通すこと:
   ```js
   function normCode_(code) { const s = String(code || '').trim(); const n = parseInt(s, 10); return isNaN(n) ? s : String(n); }
   ```
   byExtIdはrawキーなので、除外解決時は「raw一致 → 全会員をnormCode_で総当たり」の2段構え（会員数は数百件なので総当たりで問題ない）
2. **member_idの型**: シートから読むと数値になる。比較・Setはすべて `String()` を通す
3. **product_noの型**: シート書き込み時は `String()`（Sheetsの数値化→後工程422の既知問題。HANDOVER.md冒頭の注意書き参照）
4. **認証**: 新アクション3つ＋adoptは、doPost内で既存の `auditSpecialPrices` と同じ位置（ポータルセッション認証必須ゾーン）に追加する。認証より前に置かないこと
5. **LIMIT 300**: 各一覧の300件打ち切りは維持。truncated表示も維持
6. **`_spCustomersCache`** はリクエスト内キャッシュなので、addAuditExclusion→audit実行は別リクエスト＝キャッシュ問題なし
7. **unmanaged行のBカート価格がNaN** になり得る（unit_price未定義のspecial_price）。取り込みボタンはNaN行を弾く（checkbox無効）
8. **XSS**: 理由・label等の描画は既存 `esc()` を必ず通す

## 9. テスト計画（デプロイ後にTakashiと実施）
