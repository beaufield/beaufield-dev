## 0. Phase A は実施しない（経緯・重要）

当初は「ローカルPythonで差異Excelを出す（Phase A）→件数を見てからmaster-tool統合（Phase B）」の2段だったが、**Phase Aは廃止しBに直行する**（Takashi判断 2026-07-17）。理由:
- Phase Aは**PC上でBカートを直接叩く**ため、ローカルにBカートトークン（`.env`）を置く必要があった。Bに直行すればBカート突合はGAS側（既存のスクリプトプロパティ`BCART_TOKEN`）で完結し、**ローカルにトークンを置く必要が無くなる**
- Phase Bで唯一残るローカル処理は「sales.dbを読んで集計CSVを吐く」だけで、**この処理はBカートを一切叩かない＝認証情報ゼロ**
- 価値も社員が画面で見られるBに集約される

**件数のあたりはトークン不要のSQL集計で先に確認済み（2026-07-17実測）**:
- ①設定漏れ＋②価格乖離の上限＝得意先×商品で約1,260ペア。**ただし大半はBカート未登録の得意先**（7/7抽出でも未登録1,159 vs 登録済み134）。未登録得意先はBモールにログインできず誤発注リスクが無いため**①②③の対象外**（月次derive→事前登録フローの担当領域）。**画面に出る実対象は登録済み得意先分＝数十件オーダー**の見込み
- ③休眠特価の上限＝Bカート特価設定総数（先日の突合で一致160＋管理外14＋未反映4≒**約180件**）＝ごく小さい
- → **各カテゴリは既存の300件上限テーブルで十分**。件数対策のための特別なUIは不要

## 1. 目的（この機能が答える問い）

master-toolの既存「突合チェック」（v2.20.0）は **アプリのマスター↔Bカート設定** の照合なので、**マスターにそもそも載っていない特価**は見えない。本機能は **販売実績（sales.db）↔Bカート設定** を直接照合し、次を洗い出す：

| # | カテゴリ | 意味 | リスク |
|---|---------|------|--------|
| ① | **特価の設定漏れ（実績ベース）** | 販売履歴では特価で売っているのに、Bカートに特価設定が無い | **会員がBモールで通常価格のまま注文・出荷されてしまう（最重要）** |
| ② | **金額ちがい（実績ベース）** | Bカートに特価設定はあるが、実際の販売価格と金額が違う | 現場価格とBモール価格の不整合 |
| ③ | **休眠特価** | Bカートに特価設定があるが、直近12ヶ月その得意先への販売実績が無い | 棚卸し・整理候補（リスク低） |

既存「突合チェック」との違い＝**情報源がマスターシートではなく販売履歴**。両方を残す（マスター漏れは既存が、マスター未登録の実績漏れは本機能が担う）。

## 2. アーキテクチャ（データの流れ）

```
sales.db（PC・SQLite・毎日再構築）
  │  ローカルバッチ export_price_audit.py（Bカート非接続・認証情報ゼロ）
  ▼
G:\マイドライブ\<専用フォルダ>\ に集計CSV 2本を書き出し
  │  Google Drive for Desktop がDriveへ同期
  ▼
Google Drive の専用フォルダ（PRICE_AUDIT_FOLDER_ID）
  │  GAS が DriveApp で読む ＋ Bカート product_sets/customers を取得（既存トークン）
  ▼
GAS auditSalesVsBcart：正規化照合で①②③に分類
  ▼
master-tool「実績突合」サブビュー（v2.20.0の描画・取り込み・除外・遷移を再利用）
```

**確定した設計判断**:
- 集計CSVは `G:\マイドライブ` 配下の専用フォルダに置く（Drive for Desktop がマウント済みを実機確認済み）。**ローカルバッチは認証情報を一切持たない**（ファイルを書くだけ）
- Bカート取得・突合・除外・取り込みは全てGAS（既存の`BCART_TOKEN`・`fetchCustomersCached`・`normCode_`を再利用）
- 除外設定は**v2.20.0の`特別価格_突合除外`シートを共用**（テスト用得意先は両方の突合から外れる）

## 3. ローカルバッチ: `sales-db/export_price_audit.py`（新規）

> 置き場所は sales-db（sales.dbと同じプロジェクト）。⚠️ sales-db配下でも**出力先はGit管理外**（G:\マイドライブ）だが、スクリプト自体に得意先名・価格は含まないためコミット可否は sales-db の方針に従う（sales-db/はGit管理外なので実質コミットされない）。

### 役割
sales.db（read-only）を読み、集計CSVを2本 `G:\マイドライブ\<専用フォルダ>` に**UTF-8（BOM無し）**で書き出す。Bカートには接続しない。

### 出力1: `price_audit_seed.csv`（実勢特価・①②用）
`derive_special_prices.py` と同じ抽出ルールで、得意先×商品ごとに**最新売上日の価格を実勢価格として1行**に集約：
```
列: 得意先コード, 得意先名, 商品コード, 商品名, 実勢価格, 回数, 最終売上日, サロン価, 価格ばらつき数
```
SQL条件（deriveと同一）: 直近12ヶ月・`明細区分=''`・`特値!='特'`・`単価>0 AND 数量>0`・`親子コード!=''`・同一 得意先×商品×単価が3回以上・`商品.売上単価>0` かつ `|単価-売上単価|>0.01`。同一 得意先×商品 に複数価格が残る場合は**最終売上日が最新の価格を採用**し`価格ばらつき数`にdistinct価格数を入れる。
- ⚠️ 列名 `商品ｺｰﾄﾞ` は半角カナ（全角では引けない）。`売上日` はYYYYMMDD文字列
- 想定行数: 約1,260行（うち大半は未登録得意先。GAS側で会員解決できない行は自動的に対象外になる）

### 出力2: `price_audit_activity.csv`（販売実績ペア・③休眠判定用）
```
列: 得意先コード, 商品コード
```
`SELECT DISTINCT 親子コード, 商品ｺｰﾄﾞ FROM 売上明細 WHERE 売上日>=? AND 明細区分=''`（回数・特値条件なし＝1回でも売れば「動きあり」）。想定約28,800行・数百KB。

### CLI・実行
```
py -3.12 export_price_audit.py            # 既定12ヶ月・3回以上
py -3.12 export_price_audit.py --months 24 --min-count 2
```
- 冒頭で pandas import 失敗時は「py -3.12 -m pip install pandas」を案内して終了（sales-dbの2026-07障害の教訓）
- 出力先パスはスクリプト冒頭の定数 `OUT_DIR = Path(r"G:\マイドライブ\...")`。**Takashiが専用フォルダを作成してからこの定数と後述のGASプロパティを設定する**（§7セットアップ）
- **自動化**: `sales-db/取り込み実行_自動.bat` の末尾に `py -3.12 -u export_price_audit.py >> logs\...` を1行追加（毎日sales.db更新後に自動でCSVが最新化される）。加えて手動更新用に `実績突合データ更新.bat`（単体起動）も作る（メモリ feedback_bat_file_simplicity＝単一目的・pure ASCIIコマンド・日本語絶対パス直書き禁止に従う）

## 4. GAS側（Code.gs v2.21.0）

### 4-1. 定数・プロパティ
- スクリプトプロパティ `PRICE_AUDIT_FOLDER_ID` を追加（集計CSVを置く専用DriveフォルダのID）
- 定数 `const PRICE_AUDIT_SEED = 'price_audit_seed.csv'; const PRICE_AUDIT_ACTIVITY = 'price_audit_activity.csv';`

### 4-2. CSV読み込みヘルパー（新規・UTF-8）
`loadCsvFromDrive()` は`CSV_FOLDER_ID`固定・Shift_JIS固定なので流用不可。新関数を作る：
```
function loadAuditCsv_(folderId, filename) → { ok, rows, updatedAtDate }
```
- `DriveApp.getFolderById(folderId).getFilesByName(filename)`、`getDataAsString('UTF-8')`、既存 `parseCsv()` を再利用
- 2ファイルとも読み、`updatedAtDate` は seed 側を採用

### 4-3. 新アクション `auditSalesVsBcart(params)`（ポータルセッション認証必須ゾーン）
処理:
1. `loadAuditCsv_(PRICE_AUDIT_FOLDER_ID, PRICE_AUDIT_SEED/ACTIVITY)` で2CSV読込。**鮮度チェック**: seedの更新が48時間以上前なら `stale:true` と `csvUpdatedAt` を返す（画面で警告表示。処理は続行）
2. `fetchCustomersCached()` で会員。`byExtId`＋（v2.20.0で追加済みの）`normCode_`ベースの解決を使い、**`norm(ext_id)→{会員ID,会員名}`マップ**を作る（`findMemberByCode_`を流用可）
3. `bcartGetAll('/product_sets')` で商品セット。`norm(product_no)→set` と `(set_id, member_id)→特価` マップを作る（special_priceのカンマ区切りキー展開は既存`auditSpecialPrices`と同じロジックを共通関数に切り出して再利用）
4. 除外セット: `特別価格_突合除外`シートを読み、v2.20.0の`auditSpecialPrices`と同じく`excludedMemberIds`/`excludedCodes`を構築（同じ処理なのでヘルパー関数化して両者から呼ぶのが望ましい）
5. seed各行を分類:
   - `norm(得意先コード)` が除外 → excludedCount++、skip
   - 会員解決できない → `unregisteredCount++`、skip（対象外。月次derive領域）
   - 商品がBカートに無い → `noBcartProductCount++`、skip
   - Bカートにその会員×setの特価が**無い** → **①missing**（`expected_price=実勢価格`）
   - 特価が**有り**かつ金額違い → **②mismatch**（`bcart_price`と`expected_price`両方）
   - 一致 → `matched++`（出力しない）
6. ③dormant: product_setsの全special_priceエントリを走査し、`会員ID→norm(ext_id)`解決でき ∧ 除外でない ∧ `(norm(得意先コード), norm(product_no))` が activity集合に**無い** → dormant行
7. 各配列300件上限（既存踏襲）・`summary{missing,mismatch,dormant,matched,excluded,unregistered,noBcartProduct}` ・`stale`・`csvUpdatedAt` を返す
- 行に持たせる項目（v2.20.0の描画・取り込みと揃える）: `product_no, set_name, customer_code, member_id, member_name, set_id, expected_price(実勢), bcart_price(②のみ), count(回数), last_sale_date(最終売上日), salon_price(サロン価), rate(掛率%)`。①②はsource相当に「販売実績」を入れる

### 4-4. ①の「個別特価に追加」= 既存フロー再利用（⚠️v2.20.0のadoptとは別セマンティクス）
①はBカートに特価が**無い**ので、v2.20.0の`adoptUnmanagedPrices`（applied_at=now＝反映済み扱い）は**使わない**。代わりに **`saveIndividualPrices`（未反映で保存）を再利用**し、追加後にユーザーが個別特価タブで「BCARTに反映」する導線にする。フロントの一括ボタンは「✔ 選択を個別特価に追加（未反映）」とし、成功後に「個別特価タブで『BCARTに反映』を押してください」とtoast＋個別特価タブへの遷移ボタンを出す。
- 送信形式は`saveIndividualPrices`の`items`（`customer_code, product_no, unit_price, note`）に合わせる。noteに「実績突合: 履歴N回 最終YYYYMMDD」を入れる

### 4-5. doPost switch
`case 'auditSalesVsBcart': return jsonResponse(auditSalesVsBcart(params));` を特別価格系ゾーンに追加。`saveIndividualPrices`は既存。

## 6. 落とし穴（必読）

1. **正規化の一貫**: 得意先コード↔ext_id、商品コード↔product_no は必ず`normCode_`（GAS・v2.20.0で追加済み）／Python側は同等の`norm_code`を通す。ゼロ埋め差・親子コードのハイフンに注意（メモリ project_bcart_ext_id_format）
2. **CSVエンコード**: 新CSVはUTF-8。GASは`getDataAsString('UTF-8')`（`loadCsvFromDrive`のShift_JISをコピペしない）
3. **未登録得意先を①に出さない**: 会員解決できない実績は対象外（Bモール未ログイン＝誤発注リスク無し）。件数のみsummaryに
4. **①のセマンティクス**: adoptUnmanagedPrices（反映済み扱い）ではなく saveIndividualPrices（未反映）を使う（§4-4）。ここを間違えるとBカート未設定なのに「反映済み」になり漏れが残る
5. **検算（Takashiと）**: ①から数件、Bカート管理画面で本当にspecial_priceが無いことを目視。7/7に反映済みの登録済み134件が大量に①へ出るなら反映漏れかバグ（切り分け: 既存突合チェックの結果と照合）
6. **Drive同期ラグ**: バッチがG:\に書いてからGASが読めるまで数分のUP同期待ちがある。鮮度チェック（48h）で吸収。バッチはDrive for Desktop稼働が前提
7. **CSV肥大**: activity約2.8万行。GASでSetに載せる程度は問題ないが、`parseCsv`が全行メモリ展開する点に留意（数百KBなら可）
8. **300件上限**: 実測から実対象は数十件想定だが、上限と`truncated`表示は既存踏襲で残す
9. **special_price展開の共通化**: `auditSpecialPrices`内のカンマ区切りキー展開と、本関数の展開は同一。共通ヘルパーに切り出して重複を避ける
