**作成日**: 2026-08-06
**位置づけ**: `GAS配送障害_調査レポート.md`（Codexレビュー用レポート）と過去の調査・実装を統合した**実装計画**。実装はSonnetが行う。

## 1. 総合判断（レポート§9の各論点への回答）

### 1-1. 調査の到達点は信頼できる

「サーバー処理は100%正常・失われるのは結果配送のみ」という結論は、**GAS実行ログとの1:1突き合わせ**（会社80件＋自宅20件）に基づいており、n=20の統計的弱さの影響を受けない。ここは確定として扱ってよい。

一方で失敗率そのもの（32% / 8.75%）は時間帯で大きく動くため、**「何%」を根拠にした細かいチューニングはすべて過剰適合**。以後の設計判断は確率ではなく「失敗しても壊れない構造」を基準にする。

### 1-2. §7-1（applyの非冪等）の分析は妥当。ただし実害の評価を1段下げる

Codexの指摘どおり、初回申込→配送失敗→再試行で `existing_notified` 経路に入り「すでにお申し込みをお預かりしています」と表示される。ただし現行実装を確認した結果:

- この経路でも**パスURLはメールで確実に届く**（`_sendPassResendMail`）。申込データも正しく1行だけ作られる
- つまり実害は「データ破損」ではなく「**初回のお客様が混乱するUX＋重複メール**」

致命傷ではないが、10月に向けて申込が集中する時期に43%（不調時）の確率で初見のお客様を混乱させるのは避けたい。**冪等キーの導入は妥当・採用**（→§2 P1）。

### 1-3. 冪等キー方式の穴の検証（レポート§9-1への回答)

Codex提案（クライアントがUUIDを生成し全再試行で同じ値を送る）を検証した結果、以下を仕様に織り込めば穴はない:

| 検証点 | 結論 |
|---|---|
| プライバシー（列挙攻撃） | 穴なし。`request_id` はその行を作った本人しか知らないため、`pass_url` を返しても「他人のメール＋氏名でパスURLを引く」経路は生まれない。既存の「email+氏名一致では何も返さない」設計はそのまま維持できる |
| 判定順序 | **`request_id` 一致の判定を email+氏名判定より先に**行うこと。逆にすると再試行が今までどおり `existing_notified` に落ちる |
| メール重複 | `request_id` 一致（＝リプレイ）のときは**メールを送らない**。初回実行で確認メールは送信済み |
| 旧HTMLキャッシュ互換 | `request_id` が空・未指定なら**現行動作にフォールバック**。ブラウザキャッシュに旧 index.html が残っている期間も壊れない |
| 送信失敗後にフォームを直して再送信した場合 | 同じ `request_id` だと修正内容は反映されずリプレイになる。**これは受容する**（パス画面に到達すれば pass.html の編集UI＝`updateApplication` で直せる）。request_id をペイロード変化で再生成する案は複雑化に見合わないため不採用 |
| 他のエンドポイント | `applyLiff`＝`line_user_id` 引き当てで冪等（再試行は更新扱い・L2プッシュも新規時のみで二重送信なし。ただしL2実機確認の項目に含める）。`updateApplication`＝token方式で冪等。**request_id が必要なのは `apply`（index.html）だけ** |

### 1-4. クライアント側にもう1つ直すべき分類バグがある（Codex未指摘）

実測で1/80観測された「**POSTボディ喪失**」（`action` が空で到達し `不明なアクション:` が返る）は、現行の `postWithRetry` では**リトライされない**。`postOnce` はJSONが返れば成功扱いで返し、呼び出し元は `success:false` を「サーバーの確定回答」としてエラー表示するため。

しかしクライアントは常に `action`＋`data` を送っているので、`不明なアクション` / `INVALID_REQUEST` が返った＝**輸送路でパラメータが壊れた**ことを意味する。これは一時障害としてリトライすべき（P1で冪等化するので安全にリトライできる）。

### 1-5. その他の論点への回答

- **§9-2（0.66%試算）**: 計算方法は独立仮定の下では正しい。ただし失敗は連続するため保証値ではない。**これ以上この数字を精緻化しない**。最後の砦は(a)冪等化により「もう一度押す」が常に安全＝成功になること、(b)確認メールという第2の配送経路、の2つで、確率議論から構造議論に切り替える
- **§9-3（n=20で仮説否定してよいか）**: 条件間の優劣は主張できないが、否定した仮説はどれも「劇的な改善が観測されなかった」ことで実用上は棄却してよい。追加で試す価値があるのは**新デプロイ**のみ（→P0）
- **§9-4（エンドポイント別タイムアウト）**: **統一10秒×6回のまま**。GETのn=20を根拠に分岐を増やすのは過剰適合で、保守コストに見合わない
- **§9-5（案B・ポーリング方式）**: **不採用で確定**。ポーリングも同じ配送層を通る上、「サーバー側の状態は残っていて、クライアントが取り直せる」という案Bの本質的な利点は**冪等化＋リトライで既に実現される**。案Bは中規模改修に対して増分ゼロ
- **§9-6（未検証項目の優先順）**: 新デプロイA/B測定を最優先（P0・数分）。別アカウント検証・重い処理の再測定・回線同時比較は10月準備を圧迫するため**研究項目として凍結**
- **Cloudflare Workers移行（案C）**: 不採用のまま。10月に間に合わない

## 2. 実装計画（Sonnet向け）

> 🔴 実装前に `_handoff.md` の「GAS通信の実装ルール」「列を追加するときは必ず既存列の後ろ」を読むこと。
> 🔴 GASは `gas/Code.gs` のローカル編集だけでは反映されない。GASエディタへ全文反映→**新バージョンで再デプロイ**が必要。HTMLはGitHub Pagesへpush。
> 🔴 本番データに触れる申込テストはテスト用データのみで行う。

### P0: 新デプロイA/B測定（調査・実装なし・約15分）

デプロイ不調蓄積仮説の検証。費用対効果が最も高い未実施項目。

1. GASエディタで**新しいデプロイ**を作成（本番デプロイはそのまま残す。URLが2本になる）
2. `diag.html` の接続先を切り替えながら、**同じ時間帯に交互に**旧URL・新URLへ軽量POSTを各20回以上測定（時間帯交絡を避けるためA/B交互が必須）
3. 判定:
   - 新デプロイが明確に良い（例: 旧30%失敗・新0〜5%） → 本番URLを新デプロイに切り替える（4つのHTMLの `GAS_URL` ＋ `handover-secrets.md` を更新）。**その場合もP1は実施する**（配送層の不安定さ自体が消えた保証はないため）
   - 差がない → 仮説棄却として記録し、P1へ

### P1: apply の冪等キー導入＋リトライ分類修正（本命・1リリースで同時に出す）

**対象**: `gas/Code.gs`（→v0.13.0）／`index.html`（→v0.10.0）／`pass.html`・`liff.html`（分類修正とコメント修正のみ）

#### (a) サーバー側（Code.gs）

1. `applications` シートの**末尾（V列=22列目）**に `request_id` 列を追加
   - `setupSheets` のヘッダー定義に追加＋既存シート用のマイグレーション関数 `migrateAddRequestIdColumn()` を新設（`migrateAddBusinessTypeColumn` と同型・冪等に）
2. `applyApplication` を修正:
   - `data.request_id`（トリム後・最大64文字程度で切る）を受け取る
   - ロック内の既存行走査で、**最初に** `request_id` 一致（空文字は照合対象外）を探す
     - 一致 → その行の `app_id` / `pass_url`（`ticket_token` から組み立て）を `_ok({ app_id, pass_url, is_update: false, replayed: true })` で返す。**メールは送らない。行も書き換えない**
   - 一致がなければ現行どおり email+氏名判定 → `existing_notified` or 新規登録
   - 新規登録時、`request_id` をV列に保存（`_appendApplicationRow` の引数を拡張）
   - `request_id` が空のリクエスト（旧HTML）は完全に現行動作
3. （任意・観測用）`data.client_attempt` が2以上のとき、その値をログに残す（`Logger.log` で十分。シート追記はしない＝負荷を増やさない）。本番でのリトライ発生率を実行ログから拾えるようにする

#### (b) クライアント側（index.html）

1. ページ読み込み時に `crypto.randomUUID()` で `request_id` を1回生成し、**手動の再送信を含む全送信で同じ値を使う**（申込成功で pass.html へ遷移するまで不変）
2. `buildPayload()` に `request_id` を追加。`postWithRetry` のパラメータに `client_attempt` も載せる
3. **リトライ分類の修正**（`postWithRetry`）: 返ってきたJSONが `success:false` かつ error が `不明なアクション` で始まる・または `INVALID_REQUEST` の場合、輸送路の破損とみなして**リトライ対象**にする（他の `success:false` は従来どおり確定エラーとして即返す）
4. 最終失敗時（6回全滅）のエラー文言を改善: 「もう一度押してください（二重登録はされません）」に加えて「**確認メールが届いている場合、お申し込みは完了しています**」を追記
5. コメント修正: 冒頭の試算コメント「10秒×6回 → 0.12%」は計算誤り。**正しくは約0.66%（独立仮定・保証値ではない）**に書き換える（`docs/SESSION_HANDOFF.md` 記載の既知の誤記）

#### (c) pass.html / liff.html（小改修のみ）

- (b)-3 と同じリトライ分類修正を各ファイルの `postWithRetry` に適用（コードは各ファイルに複製されている）
- (b)-5 と同じコメント誤記があれば修正
- `request_id` は**導入しない**（`updateApplication`・`applyLiff` は既に冪等）

#### 完了条件（テスト手順）

テスト用データ（実在しないメール・氏名）で、curl または一時的なテストページから:

1. 同じ `request_id` で `apply` を2回送信 → 2回目が `replayed:true` で同じ `app_id`/`pass_url` を返し、**行は1行のみ・確認メールは1通のみ**
2. **異なる** `request_id`・同じメール＋氏名で送信 → 従来どおり `existing_notified:true` ＋再送メール（既存動作の非破壊確認）
3. `request_id` なしで送信 → 従来どおり新規登録（旧HTML互換）
4. `migrateAddRequestIdColumn()` を2回実行しても壊れない（冪等）
5. ブラウザ実機: 申込→パス画面遷移が従来どおり動く。DevToolsのオフライン切替等で失敗→再クリック時に同じ `request_id` が送られることを確認
6. テストで作った行は最後に手で削除（または status=cancelled）

### P2: resendPass の重複メール抑止（小粒・P1と別リリースでよい）

配送失敗が続くと最大6通の同一再送メールが届く問題（レポート§7-2）。

- `resendPass` 内で、送信前に `mail_log` シート（`_logMail` の書き込み先）を走査し、**同一宛先・type=resend・直近10分以内**の成功記録があればメール送信をスキップして `_ok({ requested: true })` だけ返す
- 🔴 `CacheService` は使わない（[[project_gas_cache_lesson]]の教訓）。mail_log の末尾数十行を見るだけで十分
- 完了条件: 同一メールで `resendPass` を連続2回叩き、メールが1通しか届かないこと・応答は両方 `requested:true` であること

### P3: やらないこと（明示的に凍結）

| 項目 | 理由 |
|---|---|
| エンドポイント別タイムアウト | n=20への過剰適合。統一10秒×6回を維持 |
| 案B（結果をシート経由でポーリング） | 同じ配送層を通る＋冪等化で本質的利点は達成済み |
| 案C（Cloudflare移行） | 10月に間に合わない。ビューフェス後に再検討 |
| 別Googleアカウント・別スクリプトでの再測定／回線同時比較 | 運用判断に影響しない研究項目 |
| 重い処理の再測定（§6-2） | 軽量pingで再現済みのため処理量仮説は運用上の争点でない |

## 3. リリース順序と全体像

```
P0 A/B測定（15分・実装なし）
  └→ 新デプロイが良ければURL切替（それでもP1はやる）
P1 冪等キー＋リトライ分類（Code.gs v0.13.0 / index.html v0.10.0 ほか）
  └→ デプロイ: GASエディタ反映→新バージョンでデプロイ→HTML push→実機確認
P2 resendPass重複メール抑止
（この後は本来の優先順＝L2実機確認 → L3 → scan.html へ戻る）
```

**この計画が終わると**: 配送層の32%障害が今後も起きる前提で、①自動リトライで大半を吸収、②リトライ・再クリックが常に安全（冪等）、③最悪でも確認メールでパスURLが届く、の3段構えになり、Google側の配送層を直せなくても運用が成立する。

## 4. 実装時の注意（再掲・事故防止）

- 列追加は**必ず既存列の後ろ**（Code.gsが列番号で読み書きしている）。V列=22列目に `request_id`
- `applications` の行走査は `rows[i][21]`（0始まり）が `request_id`。既存行はマイグレーション後も空文字なので、**空文字同士の一致で誤リプレイしないよう空はスキップ**すること
- 電話番号列（I列）のPlain Text指定など、`_appendApplicationRow` の既存の書式処理を壊さない
- `LINE連携_実装プラン.md` と `handover-secrets.md` はGit管理外。URL・IDをコミットに含めない
- コミットは1リリース1コミット（GITHUB-RULES.md 確認→commit→push）
