## 1. 結論

**「直近しか使わないのに、毎回シート全期間を読んでいる」ことが唯一かつ最大の原因。**

発注履歴・発注明細は**追記のみ**で、**発注No（`YYYYMMDD-NNN`）が日付を含み、物理的な行順＝時系列順**になっている。
一方、アプリが実際に必要とするデータは常に「直近」に限られる。

| 画面・処理 | 実際に必要な範囲 | 現在読んでいる範囲 |
|---|---|---|
| 履歴タブ（起動時にも実行） | 直近20件とその明細 | **発注履歴 全件＋発注明細 全件** |
| 履歴の明細を開く | 1発注分（数行） | **発注明細 全件** |
| 発注の保存 | 当日分＋直近の再送分 | **発注履歴 全件 ×2回** |
| 入荷待ち（提案タブ内） | 約60日分 | **発注明細 全件＋発注履歴 全件＋商品マスター 全件** |

必要なデータは**必ずシートの末尾にある**。したがって**「末尾から必要な分だけ読む」** に変えるだけで、
ほとんどの処理が O(データ量) から O(1) になる。**機能・画面・操作は一切変わらない。**

## 4. 対策

### 対策1 ★最優先: 末尾限定読み込み（tail read）

`getDataRange().getValues()`（全件）を `getRange(開始行, 1, 行数, 列数).getValues()`（末尾のみ）に置き換える。

| 対象 | 必要な範囲 | 読み方 |
|---|---|---|
| A `getOrders` 発注履歴 | 直近20件 | 末尾から読み、20件揃うまで遡る（メーカー絞込時は多めに必要） |
| A `getOrders` 発注明細 | 上記20件分の明細 | 末尾から読み、**最古の対象発注Noの先頭行に到達するまで**遡る |
| B `getOrderDetail` | 1発注分 | 同上（履歴タブは直近20件しか開けないので、ほぼ必ず末尾にある） |
| C `saveOrder` requestId | 直近の再送のみ | 末尾200行で十分（再送は数分以内に起きる） |
| D `generateOrderNo` | **当日分のみ** | 末尾200行（1日200発注は非現実的） |
| E `deleteOrder` | 対象1件 | 末尾読み → 見つからなければ `createTextFinder` にフォールバック |
| F `buildPendingOrders` | 約60日分 | 発注Noの日付が cutoff を下回るまで末尾から遡る |

> ⚠️ **固定の「末尾N行」にしないこと。** 1発注で32明細のケースが実在し（動画のデミコスメティクス）、
> 将来1日の発注件数も増える。**「必要な最古の行に到達したか」を検証し、未到達ならチャンクを倍にして
> 再読み込みする適応的な実装**にする。これで正しさを保ちながら実質O(1)にできる。

共通ヘルパーを1つ作り、各所はそれを呼ぶだけにする（実装の重複と取りこぼしバグを防ぐ）:

```js
// 末尾から chunk 行ずつ遡り、stopWhen(row) が true になる行に到達したら停止して返す。
// 到達しないままシート先頭に達したら全件を返す（＝従来と同じ結果を保証）
function readTailUntil_(sheet, numCols, stopWhen, initialChunk) { ... }
```

**この対策だけで 3-1 のA〜F（＝体感の大半）がデータ量非依存になる。**

### 対策2 ★最優先: 読む列を絞る

`getDataRange()` は**常に全列**を読む。実際に使う列はごく一部。

- F `buildPendingOrders` の商品マスター読み（[Code.gs:1312](gas/Code.gs:1312)）: 約20列 × 9,590行 → **必要なのは「コード」「仕入単価」の2列だけ**。約1/10に削減
- 発注明細（9列）・発注履歴（11列）も、用途ごとに必要列は3〜5列

行数を減らせない箇所（`lotStats` 等）にも効くため、対策1と**セットで**実施する。

### 対策3 ★推奨: 提案タブの2段読み込み（体感速度の改善）

`getOrderProposals` は現在**12種類のデータを1回で返す**（実行13〜14秒＋対策1で扱う全件スキャン）。
画面に最初に出したい「提案リスト」が、まだ見えていないセクションのデータを待たされている。

- **第1便**（`getOrderProposals`）: proposals / analyzedAt / exclusions / eol / lotOverrides / groupStatus … **提案リストの描画に必須**
- **第2便**（`getProposalExtras`）: excess / excessAcks / dead / deadAcks / **pendingOrders** … タブ内の別セクション。遅延ロード

最重量の `buildPendingOrders` が第2便に回るため、**提案リストの表示までの待ち時間が大幅に縮む**。
（通信エラー対策プランでは「対策11・スコープ外」としていたが、データ増加を踏まえ優先度を上げる）

### 対策4 ★推奨: `lotStats` の増分集計（バッチの有界化）

`lotStats`（商品ごとの発注回数・最小数量・数量のGCD）は**全期間の集計**であり、単純な期間限定はできない。
2つの案:

- **(a) 24ヶ月に限定** … 需要分析自体が24ヶ月窓なので整合的。ただし発注回数3回以上が採用条件のため、
  **古くからある低頻度商品でロット推定ができなくなる**副作用がある
- **(b) 増分集計キャッシュ（推奨）** … 「ロット集計キャッシュ」シートに `{商品コード, 回数, 最小数量, GCD}` と
  **前回処理した最終行番号**を保存し、次回は**その続きの行だけ**を読んで合算する

**(b)を推奨する理由**: 回数・最小値・GCD はいずれも**結合則が成り立つ**（追記分だけ合成しても全期間集計と数学的に一致する）ため、
**結果を1件も変えずに**有界化できる。副作用がない。

> ⚠️ 発注削除（`deleteOrder`）が起きると過去行が消え、増分集計とズレる。
> **削除時にキャッシュを破棄し、次回フル再構築する**ことで整合を取る（削除は稀なので実害なし）。

### 対策5 ★推奨: 商品マスター配信の差分化

現在アプリは**1日1回、9,590件（200KB超）を丸ごとダウンロード**している（[index.html:1373](index.html:1373)）。
GAS側には既に `PM_UPDATED_AT`（スクリプトプロパティ）があり、クライアントも `LS_MASTER_GAS_DATE` に保持済み。

- クライアントが持っている `updatedAt` をリクエストに載せる
- GAS側が一致を検出したら **`{success:true, unchanged:true}` だけを返す**（9,590行の読み込みもJSON化も行わない）

商品マスターの更新は1日1回のため、**ほとんどの起動でこの巨大な往復がまるごと消える**。

### 対策6 △任意: 入荷済み記録（手動）の剪定

追記のみで剪定されない（[Code.gs:1171](gas/Code.gs:1171)）。90日より古い行は
`buildPendingOrders` / `getReorderConfig` の判定窓の外なので不要。
週次バッチ実行時に古い行を落とす（または年1回のアーカイブ）。増加は緩やかなので優先度は低いが、
「データ量に依存しない」を徹底するなら入れておく。

### 対策7 △将来の保険: 年度アーカイブ

対策1・2が効いていれば当面不要。ただし将来 `発注明細` が5万行を超える頃には、
`発注明細_2026` のような年度シートへ退避する運用を用意しておく。**今回は実施しない**（早すぎる最適化）。

### やらないこと: 行番号の索引シート

「発注No → 行番号」の索引シートを持てば `getOrderDetail` は厳密にO(1)になるが、
**`deleteOrder` で行がずれると索引が壊れる**。復旧が難しく事故りやすいため採用しない。
対策1の適応的末尾読み込みで実用上ほぼ同等の速さが得られる。

## 6. 検証方法

**正しさの担保（最重要）**: 末尾読み込みは「必要な行を取り逃す」形でバグる。数字が静かに変わるため気づきにくい。

1. **新旧一致テスト**: 改修後の関数と、従来の全件読み込み版を**同じデータで両方走らせ、結果JSONが完全一致することを確認**する
   （`getOrders` / `getOrderDetail` / `buildPendingOrders` / `getReorderConfig` の4つは必須）
2. **境界テスト**: 1発注に30件以上の明細がある発注（デミコスメティクス 32件が実在）を含む状態で、明細が欠けないこと
3. **メーカー絞込テスト**: 履歴タブでメーカーを絞ったとき、古い発注しか無いメーカーでも20件揃うまで正しく遡ること
4. **実行時間の計測**: GAS実行ログで各アクションのbefore/afterを記録（数値を HANDOVER.md に残す）

**機能回帰（実機・iPhone Safari）**:
- 起動 → 履歴20件表示 → 明細展開 → 複製して発注 → 削除
- 提案タブ → 入荷待ち表示 → 除外・最低発注数の登録
- 週次バッチ（`--dry-run` なし）を実行し、提案件数・ロット推定が改修前と一致すること

> ⚠️ 検証で短時間に大量リクエストを流さないこと（通信エラー対策プラン §2-3 のスロットリング）。
