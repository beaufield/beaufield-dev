## 1. 結論

**アプリのロジックにもGASスクリプトにも不具合は無い。** Googleのフロントエンド（`/exec` → `script.googleusercontent.com` の結果配信）が確率的に壊れており、**症状は2種類**ある。

| 症状 | 何が起きるか | アプリでの見え方 |
|---|---|---|
| **(a) 配信404** | スクリプトは実行完了したが、結果配信が HTTP 404 のHTMLを返す | `JSON.parse`失敗 → 「通信エラー」トースト |
| **(b) POSTボディ喪失** | **リクエストのパラメータが失われた状態で実行される**。応答は404のことも、**正常な200/JSONのこともある** | 200の場合: `SESSION_INVALID`が返り、**即ログアウト→ポータル強制送還**（[index.html:1408](index.html:1408)） |

(b)が今回の新発見（v2まで見落とし）。**404が1件も起きなくても、正常に見える応答として`SESSION_INVALID`が届き、作業中に突然ログアウトさせられる**。「通信エラー」トーストだけでなく「動きがおかしい」全般の説明になる。

GASの実行ログが全て「完了」なのは、(a)(b)ともスクリプト自体は正常実行されるため（(b)は空パラメータで実行→セッション検証で弾かれて終了、これも「完了」）。**サーバー側からは原理的に見えない**。

## 3. アプリ側の該当箇所（弱点の所在）

1. **`SESSION_INVALID`で即ログアウト**: `gasGet`/`gasPost`（[index.html:1386](index.html:1386), [1408](index.html:1408)）が`SESSION_INVALID`を無条件でセッション破棄＋ポータル送還。ボディ喪失の誤爆で**正当なログイン中に突然追い出される**
2. **`res.ok`未確認・リトライ無し**: `await res.json()`が404 HTMLで例外→一律「通信エラー」（計14箇所）
3. **起動時に最大3本同時**: [1350](index.html:1350) `loadProductMasterFromGAS()`・[1360](index.html:1360) `loadHistory(false)`（await無し）＋[1372](index.html:1372) `loadMasters()`。iOS Safariはタブ破棄で`sessionStorage`が消えるため実運用では2〜3本同時が常態
4. **`saveOrder`は再送で二重登録**: [index.html:2409](index.html:2409) の`savedOrderNo`ガードは「クライアントが成功を知った後」しか効かない
5. **バッチ側**: `fetch_reorder_config`（[analyze_demand.py:569](tools/analyze_demand.py:569)）だけリトライ無し。毎朝7時のバッチが冒頭で確率的に死ぬ（書き込み系3関数は3回リトライ実装済み）

## 4. 対策（検証済み・優先順）

### 対策1 ★必須: 誤ログアウトの防止（**GAS側とクライアント側の両方が必要**）【v3新規 / v4で欠陥修正】

ボディ喪失の唯一の症状シグネチャが`SESSION_INVALID`であることはコード分岐で証明済み（§2-1）。

> ⚠️ **v4での重大な訂正**: v3は「クライアントで1回再送すれば足りる」としていたが、**これだけでは直らない**。
> [Code.gs:122-127](gas/Code.gs:122) は認証シート読み込みで**例外が出たときも `{valid:false}` を60秒ネガティブキャッシュする**。
> 本件で実証済みのGoogle側一時障害はこの読み込みでも起こりうるため、**有効なトークンが60秒間ブロックされる**。
> 即座の再送はこの汚染キャッシュを引いて、結局ログアウトさせてしまう。**GAS側の修正が先に必要。**

#### 1-a. GAS側（必須・これが本体）

`validateSession` で「**シートは読めたがトークンが無い（＝本物の無効）**」と「**そもそも読めなかった（＝一時障害）**」を区別する。

```js
  } catch(e) {
    Logger.log('セッション検証エラー: ' + e);
    return { valid: false, transient: true };   // ★ 負キャッシュせずに返す
  }
  // ここに到達＝シートを読めたがトークンが無い＝本物の無効
  const r = { valid: false };
  cache.put(cacheKey, JSON.stringify(r), 60);
  return r;
```

- `if (!sh) return { valid:false };`（[Code.gs:99](gas/Code.gs:99)）も `transient: true` にする（シート取得失敗は一時障害）
- `doGet`/`doPost` の認証失敗分岐（[Code.gs:140](gas/Code.gs:140), [221](gas/Code.gs:221)）で、`auth.transient` のときは **`SESSION_INVALID` ではなく `AUTH_UNAVAILABLE`** を返す

#### 1-b. クライアント側

| 受信した error | 扱い |
|---|---|
| `AUTH_UNAVAILABLE` | **一時障害として通常リトライ。ログアウトしない** |
| `SESSION_INVALID`（トークンを送っている） | **1回だけ全再送。2連続で初めて**ログアウト＋ポータル送還（ボディ喪失の保険） |
| `SESSION_INVALID`（トークン未保持） | 従来どおり即送還 |

これで「ボディ喪失」も「認証シートの一時障害」も誤ログアウトしなくなる。真の期限切れだけが正しく送還される。

### 対策3 ★必須: 非JSON応答の検出・リトライ・タイムアウト

**プロトタイプを本番URLで実測検証済み（§5-1）。20本で利用者に見えた失敗0件。**

```js
class GasTransientError extends Error { ... }

async function _gasFetchOnce(url, init, timeoutMs) {
  const ac = new AbortController();
  const timer = setTimeout(() => ac.abort(), timeoutMs);
  try {
    const res  = await fetch(url, { ...init, signal: ac.signal });
    const text = await res.text();                 // json()ではなくtext()
    if (!res.ok) throw new GasTransientError('HTTP ' + res.status);
    try { return JSON.parse(text); }
    catch (e) { throw new GasTransientError('non-JSON'); }
  } finally { clearTimeout(timer); }
}
```

- 再試行対象: `GasTransientError` / `AbortError` / `TypeError`（通信断）＋対策1の`SESSION_INVALID`1回
- **リトライは最大2回（計3試行）**。増やすと待ち時間が掛け算で膨張（§5-2: 3本同時が全部リトライして実測71秒）
- **タイムアウト（v3で再調整。根拠: 失敗は16〜47秒で404が返る／健全でも負荷時22〜28秒かかる実測）**
  - 保存系POST: **30秒**
  - 重い読み込み（`getOrderProposals`/`getProductMaster`/`getOrders`/`getMasters`/**`getOrderTemplate`**）: **60秒**
- バックオフ: 1秒 → 3秒

### 対策5 ★推奨: 同時リクエスト数を2に制限

原因ではないが悪化要因（8本で50%）。軽量セマフォで**同時2本**に制限する。

> ⚠️ **v4での訂正**: v3まで載せていたセマフォ実装（`if (active >= MAX) await …; active++;` 型）には
> **上限を超えて同時実行してしまうバグがある**。解放とリトライ再投入が同じ同期ブロックで起きると、
> 起床待ちの継続が走る前に新しい呼び出しが枠を横取りする。ブラウザで再現検証済み（**上限2に対しピーク3**）。
> 下記の「枠を直接引き継ぐ」実装を使うこと（同条件でピーク2＝正しい）。

```js
const GAS_MAX_CONCURRENCY = 2;
let _gasActive = 0;
const _gasWaiters = [];

function _gasAcquire() {
  if (_gasActive < GAS_MAX_CONCURRENCY) { _gasActive++; return Promise.resolve(); }
  return new Promise(resolve => _gasWaiters.push(resolve));
}
function _gasRelease() {
  const next = _gasWaiters.shift();
  if (next) next();      // 枠をそのまま次へ渡す（_gasActive は据え置き）
  else _gasActive--;     // 待ちが居ないときだけ枠を返す
}
```

- **`_gasRelease()` は必ず `finally` で呼ぶ**（例外・タイムアウトで枠が漏れると全通信が止まる）
- 取得はリトライの**各試行ごと**に行う（1試行＝1枠）
- ⚠️ 完全直列（同時1本）にしないこと — リトライとの掛け算で待ちが膨張する（§5-2で実測71秒）

   **クライアント側は `AUTH_UNAVAILABLE` を知らなくても既存の分岐で「取得エラー」表示になるだけ**（ログアウトはしない）ので実害は無いが、間を空けずに続けて出すこと。

## 6. 検証方法

```js
// ブラウザのコンソールで（セッション不要・データ不変）
const r = await Promise.all([...Array(8)].map(() =>
  gasPost({ action: 'getReorderConfig', api_key: 'wrong' })
    .then(x => x.error).catch(e => 'FAIL:' + e.name)));
console.log(r);   // 全て 'UNAUTHORIZED'（FAILなし・SESSION_INVALIDなし）になること
```

セマフォの単体確認（ネットワーク不要・**上限超過バグの回帰テスト**）:

```js
// 枠を2つ埋め、待機を1つ作り、解放と新規取得を同じ同期ブロックで行う
let peak = 0, inFlight = 0;
const enter = () => _gasAcquire().then(() => { inFlight++; peak = Math.max(peak, inFlight); });
await enter(); await enter();          // 満杯
const p3 = enter();                    // 待機列へ
inFlight--; _gasRelease(); const p4 = enter();   // ★ 同じ同期ブロック
for (let i=0;i<50;i++) await Promise.resolve();
console.log('peak =', peak);           // 2 であること（3 なら枠引き継ぎ実装になっていない）
```

実機（iPhone Safari）:

- 起動→提案タブ即タップ→最低発注数の設定→除外を連続操作して通信エラーが出ないこと
- リトライ発生時に「接続をやり直しています」表示が出て無言で固まらないこと
- **2本同時に走っても、片方の完了でローディング表示が消えないこと**（対策4の参照カウント）
- **偽トークンをlocalStorageに入れて操作→1回の再試行の後にポータルへ送還されること**（対策1-bの正常系）
- **同じ発注の保存を2回試みても発注Noが増えないこと**（requestIdの確認）
- 除外→もう一度同じ商品を除外→エラーではなく成功扱いになり、除外リストに重複が出ないこと
- ⚠️ 検証で大量リクエストを流さないこと（§2-3のスロットリング。8本＝起動数回分で十分）

## 7. 教訓（このプランの改訂履歴が示すもの）

- **v1の誤り**: 「逐次8/8成功」の少サンプルで「並列が原因」と断定 → 41本の対照実験で並列ゼロでも7.3%失敗と判明。**仮説と逆の条件での対照実験を必ず行う**
- **v2の見落とし**: 404だけを失敗と定義していた → 応答内容を分類するテスト（正解が`UNAUTHORIZED`と分かる呼び出し）に変えた瞬間、**「正常に見える応答が実は壊れている」ケース（ボディ喪失→`SESSION_INVALID`）が浮上**。失敗の検知条件そのものを疑うこと
- **v3の欠陥（v4で修正）**: 「クライアントで1回再送すれば誤ログアウトは防げる」としたが、**根拠にした`validateSession`のコードを最後まで読んでいなかった**。例外時も60秒ネガティブキャッシュする実装だったため、即座の再送は汚染キャッシュを引いて同じ結果になる。**「この対策が効く」と書く前に、効かせたい相手のコードを最後の行まで読むこと**
- **v3のもう一つの欠陥（v4で修正）**: 提案したセマフォ実装に上限超過バグがあった。**設計プランに載せるコードは、短くても実際に動かして検証する**（今回はブラウザでピーク3を再現して発見）
- GASの実行ログが「完了」でもクライアントは失敗しうる。**サーバーログとクライアント実測は別物として両方測る**
- リトライを入れる前に「そもそも1回目は実行されたのか」を確かめる手段（今回はecho URL回収）を探すと、二重実行リスクの評価が推測から事実になる
- 対策を足すと**別の前提が壊れる**（同時2本許可 → `showLoading`の単一オーバーレイが破綻）。新しい並行性を導入したら、既存のグローバル状態を全部洗い直す
